Багатопотокова симуляція складів

Інваріанти — записано до реалізації програми
1. На кожному складі meds >= 0.
2. Для кожного складу: початковий запас = залишок + сума реально взятого
   всіма його бігунами. Облік бігунів незалежний від залишку складу.
3. Загальний прибуток = сума для всіх складів:
   взята кількість * price_per_unit відповідного складу.

Це навчальна модель з вигаданими складами та випадковими подіями.

Фактичний результат перевірки (Python 3.14.0)
З Lock: 100 із 100 прогонів без порушень усіх трьох інваріантів.
Без Lock: 98 із 100 без порушень, 2 із порушенням інваріанта 1.
Перший невдалий за номером прогін — 21: Склад 2, залишок -11.
Інший невдалий прогін — 41: Склад 1, залишок -2.
Інваріанти 2 та 3 у цих серіях не порушувалися; це також перевірено.
Окремо підтверджено завершення всіх потоків і 10 спроб у кожного.
Для перевірки незалежні симуляції запускалися групами до 10 одночасно;
кожна мала власні склади та свої 5 бігунів. Паузи 0.1–0.5 с збережено.
Обидві серії разом тривали 64.0 с. Повний журнал — RUN_RESULTS.txt.
Команди --check нижче виконують ті самі перевірки послідовно, тому довше.
Порядок потоків і випадкові числа при повторенні інші: номер збою може
відрізнятися, і не кожна серія без Lock обов'язково покаже порушення.
Додатково виконано три звичайні показові прогони з прогресом: усі OK.

Як запустити у VS Code
Відкрийте саме папку threads_quest, потім Термінал → Створити термінал.
    python simulation.py
Програма сама виконає три прогони з Lock, покаже прогрес кожного бігуна,
залишки, особисті прибутки та загальний прибуток. Після кожного — assert.
Жодних сторонніх бібліотек або встановлення pytest не потрібно.

Для експерименту без блокування:
    python simulation.py --unsafe
Помилка в цьому режимі очікувана, але через випадковість не гарантована
в кожному запуску. Відсутність помилки одного разу не доводить безпечність.

Повторити серію зі 100 прогонів з assert після кожного:
    python simulation.py --check
Повторити 100 прогонів без Lock:
    python simulation.py --check --unsafe
Кожна з цих команд триває кілька хвилин, оскільки справжні паузи збережено.
Запускайте без прапорця Python -O: він вимикає assert.

Рішення, яких не визначила умова
Створено 3 склади з випадковими запасами 100–300 і 5 бігунів.
Кожен бігун прив'язаний до одного складу. Двоє ділять перший склад,
двоє — другий; це забезпечує конкуренцію за спільний запас.
Ціна на всіх складах 10 грн за одиницю, щоб спростити перевірку суми.
Імовірності: 15% спіймали, 20% частковий успіх, 65% повний успіх.
При частковому успіху випадкову кількість не вдалося взяти: вона лишається
на складі. Прибуток нараховується лише за реально взяту кількість.
«Спіймали» означає невдалу окрему спробу; наступні спроби продовжуються.
Таким чином кожен бігун виконує всі 10 спроб, як вимагає завдання.

Пояснення для захисту
Warehouse — звичайний клас складу. Зберігає назву, залишок, ціну й замок.
Runner успадковує threading.Thread — це клас окремого потоку.
super().__init__ викликає конструктор Thread, щоб потік міг запуститися.
start() запускає run() в окремому потоці. Прямий run() нового потоку не створює.
join() чекає завершення потоку. Підсумки рахуємо тільки після всіх join().
with warehouse.lock пускає всередину лише один потік для цього складу.
При виході з with замок звільняється автоматично, навіть при винятку.
Різні склади мають різні замки й можуть оброблятися одночасно.
time.sleep між спробами стоїть поза замком, щоб не затримувати інших.
min(amount, meds) бере не більше, ніж було на складі в момент перевірки.
Інваріант — правило, яке завжди має виконуватися після прогону.
assert перевіряє правило і піднімає AssertionError, якщо воно порушене.

Що таке гонка даних?
Без Lock два бігуни можуть одночасно побачити залишок 5. Кожен вирішить
взяти 5. Після двох списань залишиться -5. Окрема правильна перевірка min
не рятує: перевірка та зміна повинні бути однією захищеною операцією.
У --unsafe замок не використовується, а sleep(0.001) стоїть між обчисленням
кількості та списанням. Він збільшує шанс такого перемикання потоків.
GIL не робить всю послідовність «перевірив → списав» однією операцією.

Робота цифрового помічника
Помічник спочатку записав три інваріанти, потім створив симуляцію.
Під час перегляду коду помітив важливу деталь: коли unsafe уже спричинив
від'ємний залишок, min(amount, meds) міг би повернути від'ємну кількість
і наступна операція приховала б помилку. Додано ранній вихід при meds <= 0.
Це не виправляє гонку без замка, але не дозволяє «брати» від'ємні кількості.
Перший запуск перевірочного сценарію зупинився через кодування українського
тексту в середовищі помічника. Його повторено з UTF-8; той незавершений
запуск не включено до фінальних результатів. Подальші результати наведено
окремо і не вигадано. Студент ще має самостійно ознайомитися з кодом.
